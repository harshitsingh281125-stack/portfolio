Checked before the AI call, deliberately — a user at their limit must not spend an AI call to discover it. Over the limit → 403.

Week count and hours are computed here from the user's answers. The model is never asked for them and cannot change them.

lib/ai/gateway.ts
Product code names a tier, never a model. One file — lib/ai/config.ts — binds "reasoning" to gemini-3.5-flash.

Counted from ai_usage before dispatch. If that table can't be read it returns Infinity — fails closed, because a DB blip must not become an uncapped AI endpoint.
extractJson() → validateRoadmap(raw, contract)
Malformed once → one retry, with the nudge appended to the input, never the system prompt (that would break the cached prefix). Malformed twice → give up on purpose.
METER insert into ai_usage — including failures RULE 11
Metering only successes would under-count exactly when a broken model is burning the most quota.
WRITE roadmaps → weeks → topics → notes → recall_cards
Any insert throws → the roadmap row is deleted and the FK cascade takes the children. No half-built tree survives.
FALLBACK capped · unreachable · twice-invalid RULE 9
None of those are errors the user sees. generateSeedRoadmap() runs instead, the flow completes, and generated_from is stored as "seed" so the label outlives the toast.

Onboarding answers POST to one server route. It checks the roadmap quota before spending an AI call, computes the plan contract itself so the model cannot change the week count, then generates through the gateway — which enforces the daily cap, retries once on malformed output, meters every dispatch, and falls back to a seeded template rather than failing the request.

Embeddings go through the same gateway as completions — so they're capped and metered too. Otherwise the cap would quietly stop being a cap.

Against a curated corpus of 202 vetted documents across 26 areas.
GROUNDED the model ranks our documents
It returns a ref id per pick, never a URL. The validator resolves each ref back to a real row — so a citation becomes a link on our side of the boundary. Links can't be hallucinated because the model never types one.

Each strictly weaker than the last, each named in the response, so the UI can tell the user which one they're reading.

Persisted, so re-opening the topic costs nothing. A grounded generation spends two metered calls (embed + complete); /usage shows both, so the price of grounding is a number rather than an assumption.

Study material is retrieval-augmented. The topic is embedded, cosine-matched against a curated corpus of 202 vetted documents, and the model is asked to rank our documents by reference id — it never types a URL, so a link cannot be hallucinated. Three labelled degradation steps sit behind it: grounded, ungrounded, seeded.

Server
QUERY the due queue — one index scan RULE 13
select * from recall_cards where user_id = auth.uid() and due_at <= now() order by due_at asc;
Served by recall_due_idx (user_id, due_at). Column order is the whole point: user_id leads because it's an equality filter and what RLS matches on, due_at follows because it's both the range filter and the sort — so it's a range scan, not a full scan plus sort.
POST /api/recall/[cardId]/grade
A server route, not a client write. The row is the user's; the schedule isn't. A browser computing its own due_at could hand itself a 3650-day interval and opt out of the retention loop entirely.
schedule(state, grade, now) — pure, no clock, no DB
lib/recall/scheduler.ts · hand-rolled, no library
GOT IT climb the ladder, stretched by ease
before ease 2.5 · interval 4d · reps 2 ease 2.5 + 0.1 → 2.6 rung LADDER[2] = 14 next round(14 × 2.6/2.5) → 15d
The ladder is 1 / 4 / 14 / 30 — the cadence the UI advertises. Ease (1.3–2.8) stretches or compresses each rung per card, so a card you keep nailing drifts past the nominal gap. Past the top rung it's pure multiplicative growth.
MISSED hard reset RULE 17
ease 2.5 − 0.2 → 2.3 (penalty persists) reps → 0 next 1d — you see it tomorrow
The ease penalty survives the reset. That's the card remembering it's hard for you, so it climbs the same ladder more slowly next time.
WRITE update recall_cards · append recall_reviews
The review log is append-only — it's what session accuracy and the Progress screen's accuracy trend read from. If the log insert fails the card update stands, because the schedule is the user-visible truth.

Revision is a spaced-repetition loop on a hand-rolled scheduler. The due queue is one index range scan. Grading happens server-side because the schedule is not the user’s to compute: "Got it" climbs a 1/4/14/30-day ladder stretched by a per-card ease factor, and a miss resets to tomorrow with a penalty that persists.

Stack — Next.js App Router · TypeScript · Supabase Postgres with RLS on every table · raw SQL migrations, no ORM · provider-agnostic AI gateway · pgvector for retrieval
Tested — 248 unit tests, 81 end-to-end. The scheduler, the cap, the retry and the fallbacks are all exercised against injected fakes, so none of them need the network or the database to prove they work.
